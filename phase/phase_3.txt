PHASE 3 — Proposed Design: SSMS AI Context Management Architecture
Design only — no files modified. Every mechanism below maps to a Phase-2 finding and is buildable with zero new infrastructure (plain markdown + git + one stdlib Python script).

0. Infrastructure verdict first (as requested)
Candidate	Verdict	Reasoning
Lightweight indexing	✅ YES	One brain/INDEX.md (~3KB) becomes the retrieval layer. This is the single highest-leverage change.
Code search (grep/anchors)	✅ Already available	The harness has grep/Glob/read-by-line-range. The INDEX just makes it targeted — no new tooling needed.
Caching	✅ YES — but git-based, not custom	Freshness stamps in INDEX + git diff since last-sync. The repo itself already is the persistent cache across sessions; don't build a second one.
Semantic search	❌ NO	Corpus is ~43KB ≈ 10k tokens. At this scale grep + a fact-map beats embeddings on every axis, and embeddings add a staleness problem — the exact disease being treated.
RAG / vector DB	❌ NO	Adds chunking, embedding jobs, a store, and retrieval errors, to index a corpus that fits in one context window. Revisit only if the knowledge base exceeds ~200KB or the team grows.
Consistency checker script	✅ YES — the only new code	scripts/check_context.py, stdlib-only, ~120 lines. Converts the audit's "exhortative checklists" into mechanical verification. This is what makes auto-sync trustworthy.
Design principle: the architecture is flat files + git as the change-detection engine + one verifier script. Nothing else.

Core invariant (fixes the audit's root disease): every fact has exactly one home. Prose copies are replaced by pointers. Any fact stated twice is a defect the checker flags.

2. The five mechanisms
A. Context Loading Strategy
Essential (every session, ~800 tokens):

Auto-injected slim AGENTS.md (~600 tok): identity, 6 non-negotiables (unchanged), plus a 10-line loading router.
The router's rules:
Read brain/INDEX.md header + STATUS first (≈500 tok).
Code wins over docs when they disagree (C1/C3 resolution rule).
Never read whole bll_db.sql / req.txt / engine files without an INDEX anchor.
Task-specific (per task, via INDEX rows):

INDEX §2 Module map gives, per module: registry line, hook name, table, route, perm slug, doc anchor → the AI reads those line ranges (20–60 lines each), not whole files.
Engine access becomes surgical: e.g. outlet task = modules.py:221–298 + hooks.py:358–420 + relevant form.html section instead of 73KB of engine.
Historical (on demand, tagged):

DECISIONS.md filtered by module tag; VERIFICATION_LOG.md tail; git log with the new module: action (T-xxx) convention.
Loading rule: read history only for (a) "why is it like this" questions, (b) before changing an existing behavior, (c) at handover.
Conditional context (explicit IF/THEN table, lives in INDEX §4):

IF task involves…	THEN read	ELSE skip
schema / DDL	ddl.sql header + relevant CREATE TABLE	req.txt
DDL-fidelity dispute	req.txt (targeted section)	—
data shape reference	live DB query (SELECT … LIMIT)	bll_db.sql whole-file
new master module	AGENTS checklist + INDEX §2 row of one similar module	all three docs
business-rule change	BRD rule ID → then code anchor	PRD/SRS full read
release / handover	STATUS + VERIFICATION_LOG tail	everything else

Module mapping = §2 rows; Dependency mapping = the deps column (outlet → category_type/depot/depot_store) + hook-level cascade notes (item status → item_batch).
Document relationships = §3 + the rule chain: BRD rule-ID → PRD journey → SRS FR → code symbol. One-way derivation, no restatement.
Retrieval rules = §4 table + two hard rules: (1) facts from §1 are never re-derived from prose; (2) an INDEX row is trusted only if its last-sync commit ≥ HEAD — else re-verify that row only (see C).
C. Change Detection
Git-based, zero new infrastructure:

Session start: git log --oneline -5 + compare HEAD against INDEX's synced at commit.
HEAD == stamp → trust INDEX & STATUS wholesale; skip all docs. (Objective 2 satisfied: unchanged docs are never re-read.)
HEAD > stamp → git diff --stat <stamp>..HEAD → changed paths identify which INDEX rows/docs to re-verify. Re-index only those rows (targeted line-range reads), never whole documents.
Content-based validation (catches what mtimes can't): scripts/check_context.py re-derives ground truth from code (counts MODULES, SEED_PERMISSIONS, SEED_CATEGORY_TYPES, reads LEVEL_PREFIX, greps status='PENDING') and diffs it against INDEX/STATUS claims + resolves anchors. Drift → exit non-zero with a per-row report → the AI fixes exactly those rows.
Anti-blind-trust rule in AGENTS.md: before acting on any doc-stated fact, confirm it's in INDEX §1; if it's only in prose, treat as suspect and verify against code.

Identification: T-nnn ids; source link back to the original MY_WATCHER text (archived under brain/archive/).
Dependencies: explicit deps: field; blocked tasks list separately; the AI resolves order at session start instead of guessing.
Status: ready / blocked / in_progress / done — one IN_PROGRESS per session.
Archiving: DONE is append-only one-liners (id·date·commit·module·result). MY_WATCHER.txt becomes a raw inbox: the AI drains it into TASKS.md at session start and leaves a tombstone ( drained → T-014..T-016, 2026-11-11), so the user keeps their familiar workflow.
Next-session handover (objective 7): end-of-session ritual (see workflow below) writes three things: TASKS.md IN_PROGRESS+next-steps, STATUS.md refresh, INDEX re-stamp after the checker passes. The next session needs ~800 tokens to resume fully — versus today's ~10k re-orientation.

E. Memory Synchronization
Triggered once, at task completion (not mid-task):

Update only what the task touched (fixes outlet-style drift at 5% effort): INDEX module row (if registry/hook changed) → STATUS counts (if add/delete) → TASKS row → VERIFICATION_LOG entry. DECISIONS.md only if a decision was made. PRD/SRS only if behavior changed, by editing the rule-ID row, not prose restatements.
Duplicate prevention: checker scans non-canonical files for canonical phrases (2100-12-31, {id}140, PENDING/INACTIVE, MG/BG/CG/FG, #1877f2, admin123) → flags any appearance outside its declared home (H1 enforcement).
Historical preservation: DECISIONS.md and VERIFICATION_LOG.md are append-only; superseded decisions get superseded-by: D-nnn instead of deletion.
Consistency validation: the checker must pass before the closing commit — it is the gate that replaces "AI remembers the 8-file checklist".
