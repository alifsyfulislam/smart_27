CRITICAL PRIORITY
C1. Three-way conflict on hierarchy auto-codes — the docs can make the AI "fix" correct code into broken code [ACTUAL PROBLEM] (your area #7)
Description: The hierarchy prefix map exists in three contradictory versions:
Code truth (app/hooks.py:6): LEVEL_PREFIX = {0:"MG", 1:"BG", 2:"CG", 3:"FG"}
Seed + most docs (setup_database.py:91-94, AGENTS.md:7, PRD.md:61, SRS.md:50, README.md:31, and hooks.py's own docstring at line 13): CG/BG/TG/FG
BRD BR1 (updated in commit 7279a94): MG001/BG001/CG001/FG001 — matches the code
req.txt is internally contradictory: sample values are CG001/BG001/TG001 while the comments say "here MG is prefix of level".
Root cause: No single source of truth + fact replicated in 5+ files. Commit 7279a94 fixed one copy (BRD) and left the other four docs, the seed data, and the hooks.py docstring stale. Note the seed emits CG001→TG001 codes the generator itself can never produce (it would emit MG### for company, CG### for type) — seeded data and generator disagree.
Affected files: app/hooks.py (6 vs 13), AGENTS.md, docs/PRD.md, docs/SRS.md, README.md, scripts/setup_database.py, docs/BRD.md (the only accurate one), req.txt.
Token impact: Reconciliation forces reading all 5 copies (~1–2k tokens) plus the reasoning overhead of deciding which is true — an AI without code access has no way to resolve it.
Quality impact: Highest-severity failure mode in the repo. An AI trusting AGENTS.md/PRD/SRS (the files AGENTS.md itself calls authoritative) will "correct" hooks.py to CG/BG/TG/FG and silently corrupt user-facing business keys (level_id codes) for every new hierarchy node.
Recommendation: Pick the canonical map once (business decision: MG/BG/CG/FG per code, or CG/BG/TG/FG per original requirements), then implement it in exactly one place — hooks.py — and replace every prose copy with a pointer: "codes: see hooks.py LEVEL_PREFIX". Also fix the seed data and the docstring in the same change.

HIGH PRIORITY
H1. The 8-file doc-sync contract makes every change a documentation project, and duplication is its direct cause [ACTUAL PROBLEM] (your areas #1, #4)
Description: Because every business fact is replicated 4–8× (see evidence table), AGENTS.md §6 must mandate updating 8 files, and the AI must read all 8 before safely writing any — the mandatory reading list is ~35.6KB ≈ 9k tokens per change, and the write-back is ~5 file-edits per business rule change. Git proves the cost: brand-modified v3 = 6 doc files edited for one UX feature.
Root cause: BRD/PRD/SRS/brain/SKILL/README/PROMPTS were each written as if standalone-readable, so each restates the rules (default batch, default stores, soft-delete semantics, palette, codes) instead of referencing them.
Affected files: all 9 knowledge files (systemic).
Token impact: Largest structural token cost in the workflow — ~9k tokens/change in reads + writes, repeated every feature. Eliminating cross-copies cuts this to ~2–3k.
Quality impact: Duplication is the root cause of C1, C2, C3 (every copy is a drift surface). It also slows the AI: reconciling 8 files before a 3-line code change invites shortcut behavior (which is exactly how outlet drift happened).
Recommendation: Adopt a single-source-of-truth layout: BRD keeps only needs (rules as numbered IDs, no mechanics), PRD references rule IDs, SRS references code symbols (hooks.py LEVEL_PREFIX, crud.py status), brain holds only decisions + status, SKILL holds only conventions not elsewhere stated. Rule of thumb to enforce in AGENTS.md: any fact stated twice is a defect.
H2. MY_WATCHER.txt is an append-only pile — completed tasks permanently tax every session [ACTUAL PROBLEM] (your areas #11, #12, #1)
Description: Git-traced growth: 0B (initial) → 536B (8b10af5) → 7,042B (7279a94, +151 lines added alongside the outlet code). The v1.0.0-era specs (menu/brand/item/item-batch — all completed and verified per PRD acceptance criteria) still occupy ~110 lines (~4KB) at the top of the file, undifferentiated from the current outlet task. There are no status markers, IDs, priorities, or done-tombstones (my grep for DONE/[x]/status hits only substrings like "download"). Raw DDL (sm_client, 65 lines) is pasted inline, duplicating what now also lives in ddl.sql.
Root cause: The file has no format — it's a transcription of chat messages. Nothing marks lifecycle, and committing it with each feature (which does preserve history) also means the pile is permanent and versioned.
Affected files: MY_WATCHER.txt (7.2KB, 153 lines).
Token impact: ~1.8k tokens re-read every session, growing unboundedly; plus the reasoning cost of guessing which bullets are still open — the file's oldest half is pure dead weight.
Quality impact: Two failure modes: (a) re-doing completed work (nothing says the menu/brand/item items are shipped), (b) missing live items buried under stale ones. Also risk: the AI treats stale spec lines (e.g. old brand/delete-button rule) as current requirements since no timestamp exists.
Recommendation: Give the file a minimal schema — ## OPEN / ## DONE (date, commit) sections, or one line per task: ID | status | deps | module | text. Archive DONE entries on completion. Move pasted DDL out (point at ddl.sql/bll_db.sql instead).
H3. Session-to-session knowledge loss: verification evidence exists nowhere durable [ACTUAL PROBLEM] (your areas #10, #9)
Description: Every session re-verifies by live HTTP + audit-log checks (per AGENTS/SKILL), but the results are never persisted. H4. Any small change requires loading the whole engine — monolith structure drives base token cost [IMPROVEMENT with real present-day cost] (your areas #2, #3)
