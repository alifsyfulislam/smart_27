2. The seven questions — actual traced workflow
Q1. How does the AI start a session?
AGENTS.md is injected automatically into the system context by the agent harness (confirmed — it arrived in my own context at session start, without any user action). It carries the project identity, 6 non-negotiables, the verification commands, and the "new master module" checklist.
The ssms skill is auto-discovered from .agents/skills/ssms/SKILL.md (frontmatter name/description) and appears in the skill list; it triggers when a task matches "FastAPI/Jinja/MySQL master-data changes".
Nothing else loads by itself. MY_WATCHER.txt, docs, brain, prompts are all opt-in reads — the user must point the AI at the task (typically "read MY_WATCHER.txt"), or the AI must choose to look.
Despite the name, nothing watches MY_WATCHER.txt. It is a plain scratch/intake file the human maintains by hand.
Q2. How does it read project documentation?
Docs are read on demand, in derivation order: BRD (business rules BR1–BR11) → PRD (page journeys, hook table, acceptance criteria) → SRS (architecture diagram, FR1–FR6, data model, ops). Each header explicitly declares its dependency ("PRD depends on BRD", "SRS implements PRD"), so the chain is self-documenting.
AGENTS.md §6 only mandates writing the docs, not reading them. In practice the agent reads the relevant section when behavior changes, using SKILL.md's doc-update checklist as the map ("BRD → business rules; PRD → journeys + acceptance; SRS → architecture/FR").
Q3. How does it retrieve project context?
Four retrieval paths, all manual read/grep, no index beyond these:

brain/PROJECT_BRAIN.md is the designated entry point — its "Where things live" section is the only explicit file index (hooks → app/hooks.py, UI → app/modules.py, schema → scripts/ddl.sql, …).
scripts/ddl.sql header comment is the schema change-log ("what was added vs. the requirements' DDL and why").
req.txt + bll_db.sql are the frozen ground truth for schema fidelity (the expiary_date typo rule is anchored here).
Git history for feature lineage.
Q4. How does it execute daily tasks?
The traced loop (visible in the actual code and git diffs):

Intake from MY_WATCHER.txt (tasks are often pasted as raw text + raw DDL, e.g. the whole sm_client CREATE TABLE is in there verbatim).
Register the module in app/modules.py (MODULES dict + MODULE_ORDER/PERM2SLUG) — outlet confirmed present at app/modules.py:221 with table: sm_client, create_hook: outlet.
Business rules as a hook in app/hooks.py (registered under HOOKS), so every write flows through crud.py → audit.
Schema into scripts/ddl.sql (with status column if soft-delete; header comment updated), permissions seeded in scripts/setup_database.py.
Verify per AGENTS.md/SKILL.md: start uvicorn on port 8027 → POST /login admin/admin123 → curl the module flows → confirm sm_audit_log grew. The cookies/cookies2 curl cookie jars are the physical residue of this loop (cookies2 decodes to session uid view1 — a VIEWER user, i.e. permission-negative testing was actually done). server.log confirms auto-bootstrap ran ("DB bootstrap OK (smart_27)") and one port-collision restart.
Template/upload flows tested with the two *.xlsx artifacts in the root.
Q5. How does it update Project Brain?
brain/PROJECT_BRAIN.md is hand-edited by the AI; its own header sets the contract: "Living memory for anyone picking up this project. Update on every change."
Structure: dated Status ("as of 2026-11-09") → Key decisions & why (numbered, with rationale) → Gotchas learned the hard way → Where things live → Next candidates (backlog).
Practice check: brand-modified v3 (Nov 9) updated brain + all 3 docs + README ✔; the outlet module commits (Nov 10) did not — brain still reads "as of 2026-11-09", and PRD/SRS/SKILL/PROMPTS were untouched (see §4, Finding 2).

Q7. How does it handle task completion and session handover?
There is no formal handover artifact or end-of-session script. Handover is entirely the state of the files when the session ends:

Clean git tree (git status clean) — the commit is the handover boundary.
Updated doc set + brain = the next session's briefing (brain's header literally says it's for "anyone picking up this project").
PROMPTS.md hands over operations (7 reusable prompt templates an operator/agent can run against the live app).
MY_WATCHER.txt carries the residual backlog — unfinished requirements simply remain in the file for the next session.
