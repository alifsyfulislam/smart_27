
# Business Requirements Document (BRD)
## Secondary Sales Management System (SSMS)

**Version:** 1.0.0 · **Date:** 2026-11-05 · **Database:** smart_27 (MySQL 8 / MariaDB 10.4) · **Stack:** FastAPI web app (Flutter app planned later)

---

## 1. Purpose

SSMS manages the **master data** required before secondary-sales transactions can run:

- Item hierarchy (Company → Brand → Type → Flavor)
- Items and their batches
- Distributors (depots) and their stores
- Outlets and their distributor, store, and category relationships
- Fieldforce structure, employee assignments, and visit plans
- Data-definition master (category types)

It enforces role-based access control and maintains a central audit trail of every master-data change.

## 2. Scope

**In scope (this release):**

1. **Item Info** — Brand (item hierarchy), Item, Item Batch, Rack.
2. **Distributor Info** — Distributor, Distributor Store, Item Stock, Rack Stock.
3. **Outlet Info** — Outlet (client master with distributor, store, and category linkage).
4. **Fieldforce Info** — National Structure (`sm_top_level`), Field Structure (`sm_level`), Employee Master (`sm_rep`), Supervisor Area Assignment (`sm_supervisor_level`), PSR Visit Plan (`sm_visit_plan`), Outlet Exceptional Visit Plan (`sm_client_visit_plan`). PSR Area (`sm_rep_area`) is consolidated into PSR Visit Plan.
5. **Settings** — Category Type (data definitions for columns like `depot_category`, `store_type`, `pack_size`, `unit_type`, `item_category`).
6. **Access Control** — User / Role / Permission (ACL) with mapping tables.
7. **Records** — Central audit log written only by the application.

**Out of scope (future):** Sales orders, requisitions, deliveries, payments, invoicing, and the Flutter mobile client.

## 3. Business Rules

| # | Rule |
|---|---|
| BR1 | Item hierarchy levels are created manually (no integration). Levels: Company (C*) → Brand (B*) → Type (T*) → Flavor (F*), auto-coded per the level prefix map (`app/hooks.py LEVEL_PREFIX`; values in `brain/INDEX.md` §1) with parent path columns `level0..level3`. |
| BR2 | Leaf flag invariant: a hierarchy node has `is_leaf=1` **if and only if it has no ACTIVE child** — recomputed automatically on create, update, soft delete, and restore. Renaming a level propagates through descendant path columns. |
| BR3 | Items come from integration or manual creation; every item automatically gets a **default batch `1` with expiry 2100-12-31** (`sm_item_batch`). |
| BR4 | Items are tagged sequentially with Company > Brand > Type > Flavor from the hierarchy. |
| BR5 | Distributors come from integration or manual creation; every distributor automatically gets two default stores — **Commercial** and **Damage** (`sm_depot_store`; ID pattern: `app/hooks.py depot_after_create`, values in `brain/INDEX.md` §1). |
| BR6 | All master modules support: create, view, edit, **soft delete (status → PENDING)**, restore, and **template-based Excel batch upload**. |
| BR7 | Every master-table change (create/update/delete/restore) is recorded in the central log `sm_audit_log` **by the application only** — no DB triggers. |
| BR8 | Users are restricted by ACL: permissions like `item.view`, `item.create`, `item.edit`, `item.delete`, `item.import`, grouped under modules; roles bundle permissions; users get roles and/or direct permissions; a super-admin bypasses checks. |
| BR9 | `sm_category_type` feeds the value lists used by other modules (depot category, store type, item category, unit type). |
| BR10 | A brand (hierarchy) level may carry an **image**: uploaded files are stored under `app/static/uploads` as `{table}_{name-slug}_image_{timestamp}.{ext}` (PNG/JPG/GIF/WEBP, max 5 MB), and the generated link is saved in `image_path`. Editing can preview and replace the image; leaving the file input empty keeps the current one. |
| BR11 | From the Brand **edit page**, a user can add one or many **child levels** in a single submit (names deduped; each child flows through the normal auto-code/path/audit pipeline). A Flavor (depth 3) cannot have children. |
| BR12 | **Outlet Info** (`sm_client`): Features auto-generated numeric `client_id` starting from `1000001` following the Employee ID form pattern (hidden on create form with placeholder, readonly and immutable on edit form with tabindex -1 and non-editable styling). Sourced with Beat (`area_id`) as a required select from `sm_level` (depth 3) with a Route filter on create/edit forms to easily select beats among large numbers; `area_name` auto-resolved and stored. When creating or editing an outlet, the selected Beat must have an assigned distributor in `sm_level`; if unassigned, create/edit is rejected with a validation error. When valid, `depot_id` and `depot_name` are recorded on `sm_client`, and that distributor's default Commercial store from `sm_depot_store` (`store_type='COMMERCIAL'`) is recorded as `store_id` and `store_name`. Distributor, Distributor Store, and Old Outlet ID are excluded from form inputs (`in_form=False`). Profile photo upload (`image_path`) mirrors `sm_item` image handling (PNG/JPG/WEBP up to 5 MB stored under `/static/uploads/sm_client_{name}_{timestamp}.{ext}`). Customer type is auto-generated as `category_id\|category_name` from `sm_category_type` (groups `OUTLET_CATEGORY` and `OUTLET_SUB_CATEGORY`). The list view provides "All Beat" (`area_id`) and "All Distributor" (`depot_id`) dropdown filters. |
| BR13 | Dynamic dropdown and foreign-key select fields (hierarchy levels, item lookup, distributor lookup, store lookup) must display selectable options in canonical `ID \| Name` format (e.g. `BG001 \| Kurkure`). In item create and edit forms, hierarchy cascade options must remain fully visible and searchable without placeholder filter occlusion. On edit, previously saved hierarchy associations must auto-hydrate sequentially from database values. |
| BR14 | **National Structure** (`sm_top_level`): 4-tier tree: National (depth 0, prefix `H`) > Area (depth 1, prefix `A`) > Zone (depth 2, prefix `Z`) > Territory (depth 3, prefix `T`). Territory is the maximum depth (leaf; cannot have children). Auto-incremental codes (`H0001`, `A0001`, `Z0001`, `T0001`) with parent lineage columns `level0..level3` and dynamic `is_leaf` recomputation. |
| BR15 | **Field Structure** (`sm_level`): 4-tier market coverage tree: Territory (depth 0, prefix `T`) > Town (depth 1, prefix `TW`) > Route (depth 2, prefix `R`) > Beat (depth 3, prefix `B`). In create and edit forms, Parent Level options are sourced dynamically from active Zones in `sm_top_level` (`depth 2`, `status='ACTIVE'`), and Territory name/ID suggestions are dynamically filtered and loaded based on the selected Parent Zone (`sm_top_level depth 2 → depth 3`, `parent_level_id = zone_id`), preventing mismatched selections and inserting `level_id`, `level_name`, `parent_level_id`, and `parent_level_name` directly from National Structure. Beat is the maximum depth (leaf; cannot have children). Auto-incremental codes (`TW0001`, `R0000006`, `B0000033`) for depths > 0 with lineage columns `level0..level3` and dynamic `is_leaf`. Distributor tagging (`depot_id`) is removed from create and edit forms (`in_form=False`) to streamline level management; existing distributor mappings are preserved on edit. |
| BR16 | **Employee** (`sm_rep`): Managed via integration or manual creation; unique on `(cid, rep_id)` where `rep_id` accepts NULL for external integration records, and unique on `(cid, rep_username)` (`UNQ_REP_USERNAME`). User type is sourced dynamically from `sm_category_type` (`EMP_USER_TYPE`: `rep` = Pre Sales Executive / PSR, `sup` = Supervisor / Manager, `dm` = Delivery Man / DM). Dynamic cascading dropdown: User Type is selected first, filtering Designation options (`rep` loads only `PSR`, `dm` loads only `DM`, `sup` loads all designations except `PSR` and `DM`). On create (`/rep/create`), `Employee ID` (`rep_id`) is hidden (`hide_on_create=True`) to avoid user confusion and is auto-generated on save with designation prefix code: `PSR0001`, `DM0001`, `HOS0001`, `SOM0001`, `ASM0001`, `ASE0001`, `CE0001` (4-digit zero-padded sequence); on edit (`/rep/edit/{id}`) and view (`/rep/view/{id}`), `rep_id` remains visible (readonly on edit). The `rep_username` ("Username") field is captured on manual forms (required) and verified for uniqueness. Dates `dob` (Date of Birth) and `doj` (Date of Joining) are optional across create, edit, and Excel import (stored as `NULL` when omitted). Passwords entered in plain text are encrypted using MD5; editing with an empty password retains the existing hash. Profile photo upload (`image_path`) mirrors `sm_item` image handling (PNG/JPG/WEBP up to 5 MB stored under `/static/uploads/sm_rep_{name}_image_{timestamp}.{ext}`). Form fields arranged logically with Photo / Image (`image_path`) positioned directly before Note; Distributor (`depot_id`) is excluded from create/edit forms (`in_form=False`) and preserved on edit. |
| BR17 | **Supervisor Area Assignment** (`sm_supervisor_level`): Supervisors (`sm_rep` where `user_type='sup'`) can be assigned to any administrative or field tier across National Structure (`sm_top_level`) or Field Structure (`sm_level`), stored with `sup_id`, `level_id`, and unified `level_depth_no`. Depth is computed as `sm_top_level.depth` for National levels (National=0, Area=1, Zone=2, Territory=3) and `sm_top_level max depth (3) + sm_level.depth` for Field levels (Territory=3, Town=4, Route=5, Beat=6). Form `/supervisor-level/create` and edit provide a Hierarchy Tier Filter (`f-hierarchy_tier`) that instantly narrows down the searchable `level_id` dropdown (`data-searchable`) by administrative/field tier with live calculated depth badge indication, eliminating search difficulty on large datasets. |
| BR18 | **PSR Area Consolidation & Auto-Sync** (`sm_rep_area`): PSR Area is consolidated under PSR Visit Plan and removed from sidebar navigation (`MODULE_ORDER`). Management of PSR area assignments flows directly through PSR Visit Plan (`sm_visit_plan`) creation, Excel import, updates, soft delete, and restore: assigning a Beat (depth 3) provisions that Beat into `sm_rep_area`; assigning a Route (depth 2) auto-provisions the Route and cascades all its active child Beats into `sm_rep_area` as `ACTIVE`. Soft-deleting or deactivating visit plans marks `sm_rep_area` rows as `PENDING` if no active visit plans remain for that representative and area. Restoring a plan restores matching `sm_rep_area` rows to `ACTIVE`. |
| BR19 | **PSR Visit Plan & Hierarchy Tier Filter** (`sm_visit_plan`): Managed under Fieldforce Info (`/visit-plan`). Create and edit forms provide a Hierarchy Level Tier Filter (`#f-visit_plan_tier`) that instantly filters the searchable `area_id` dropdown (`data-searchable`) between Routes (depth 2) and Beats (depth 3) from `sm_level`, displaying Route lineage and Depot context. Representative (`rep_id`) is a searchable single-select with placeholder "Type to search Representative…" and default empty option "-- Select Representative --", matching Delivery Man input behavior. Distributor selection (`depot_id`) is excluded from forms (`in_form: False`) and inherited from field area or preserved on edit. Order collection days are sourced dynamically from `sm_category_type` (`WEEK_DAYS`). Delivery day is auto-calculated and removed from forms (`in_form: False`): Saturday through Wednesday map to the next calendar day; Thursday and Friday map to Saturday. Delivery Man selection is searchable with placeholder "Type to search Delivery Man…". Order collection day filters are removed from the list view. Succeeded creates and Excel imports auto-synchronize to `sm_rep_area`. Unique on `(cid, rep_id, area_id, order_col_day)`. |
| BR20 | **Outlet Exceptional Visit Plan** (`sm_client_visit_plan`): Enables custom, non-standard outlet scheduling by mapping an outlet (`client_id`) within an area (`area_id`). Create and edit forms present Area / Beat (`area_id`) first, equipped with a Route filter, followed by dynamic cascading Outlet selection (`client_id`) filtering outlets by the selected Beat with active count badge. Visit frequency is sourced dynamically from `sm_category_type` (`FREQUENCY_TYPE`: `WEEKLY`, `BI_WEEKLY`, `MONTHLY`, `FORTNIGHTLY`). Weekly cycle flags (`w1`..`w5`) and weekday matrix flags (`sat`..`fri`). The list view provides "All Beat" (`area_id`) and "All Distributor" (`depot_id`) dropdown filters. |
| BR21 | **Rack Master** (`sm_rack`): Managed under Item Info (`/rack`). Supports manual creation, view, edit, soft delete, restore, and Excel import. Mirrored image upload parity with `sm_item` (PNG/JPG/GIF/WEBP up to 5 MB saved under `app/static/uploads/sm_rack_{slug}_image_{timestamp}.{ext}`). Unique on `(cid, rack_id)`. The `rack_id` is immutable on edit. Preserves historical schema column expiry date. |
| BR22 | **Item Stock** (`sm_depot_stock_balance`): Managed under Distributor Info (`/depot-stock-balance`) (renamed from Distributor Stock). Records inventory balances per distributor, store, item, and batch. Unique on `(cid, depot_id, store_id, item_id, batch_id)`. Manual creation, editing, deleting, and Excel importing are strictly prohibited (`no_create: True`, `no_edit: True`, `no_delete: True`, `no_import: True`; create permission `depot_stock_balance.create` removed from catalogue reducing total seeded permissions to 80; action endpoints redirect with error flash and corresponding buttons are suppressed). Does not carry a `status` column. Features automatic stock row provisioning with quantity 0 and blocked quantity 0 across four triggers: (1) creating/importing an item auto-provisions across all batches of that item &times; all depots &times; all depot stores, (2) creating a batch auto-provisions across that batch &times; all depots &times; all depot stores, (3) creating a distributor auto-provisions across all its stores &times; all items &times; all batches, (4) creating a store auto-provisions across that store &times; all items &times; all batches. Provides "All Distributor Store", "All Item", and "All Distributor" filter dropdowns on the list view. Preserves historical schema column expiry date. |
| BR23 | **Distributor Store Filter & Readonly Distributor** (`sm_depot_store`): The `/distributor-store` list page provides a Distributor dropdown filter. On `/distributor-store/edit/{id}`, the Distributor selector is disabled/non-editable (`readonly_on_edit=True` with hidden input fallback and server-side immutability in `depot_store_prepare`), preventing reassignment to another distributor. |
| BR24 | **Distributor Status Cascade & Readonly Distributor ID** (`sm_depot`): Inactivating (`status='INACTIVE'`) or soft-deleting (`status='PENDING'`) a Distributor automatically cascades that status change to all its child stores in `sm_depot_store`. Restoring (`status='ACTIVE'`) a Distributor cascades `ACTIVE` status back to its child stores. On `/distributor/edit/{id}`, Distributor ID (`depot_id`) is strictly non-editable (`readonly_on_edit=True` with server-side immutability in `depot_prepare`). |
| BR25 | **Form Streamlining & Redundant Field Elimination**: (1) In Item Batch (`sm_item_batch`), the Name input field is removed from create and edit forms (`in_form: False`) as the Item selector already renders `item_id \| item_name`; the batch name is auto-populated from `sm_item.name` on save. (2) In Distributor (`sm_depot`), Town and Town ID input fields are removed from create and edit forms (`in_form: False`); existing town values are preserved on edit, and default to `"-"` on new creation; Town remains in list view and Excel bulk import. (3) In Supervisor Area (`sm_supervisor_level`), the Supervisor selector includes an empty default option and placeholder "Type to search Supervisor…". (4) In Field Structure (`sm_level`), Distributor is removed from Town create/edit forms (`in_form: False`). (5) In Employee (`sm_rep`), module title is renamed to "Employee" and Distributor is removed from create/edit forms (`in_form: False`). (6) In PSR Visit Plan (`sm_visit_plan`), Distributor is removed from create/edit forms (`in_form: False`). |
| BR26 | **Rack Stock** (`sm_depot_rack_stock_balance`): Managed under Distributor Info (`/depot-rack-stock-balance`) (renamed from Distributor Rack Stock). Read-only inventory balance and tracking module for company display racks issued to outlets across distributors and stores. Tracks distributor (`depot_id`), outlet (`client_id`), rack (`rack_id`, `rack_code`), condition (`d_r_condition`), issue date, and expiry date. Manual creation, editing, deleting, and Excel importing are strictly prohibited (`no_create: True`, `no_edit: True`, `no_delete: True`, `no_import: True`; action endpoints redirect with error flash and action buttons are suppressed across the UI). Gated by permission `depot_rack_stock_balance.view` (total seeded permissions: 81). Filtered by status, distributor, and rack ("All Rack"). |
| BR27 | **Foreign Key View Presentation Standard (`id — name`)**: Across all module record view pages (`/{slug}/view/{id}`), foreign key identifiers are formatted in standard `ID — Name` (em-dash separated) format, resolving human-readable names alongside codes: Distributor (`depot_id — depot_name`), Supervisor (`sup_id — sup_name`), Representative (`rep_id — rep_name`), Delivery Man (`delivery_man_id — delivery_man_name`), Beat (`beat_id — beat_name`), Item (`item_id — item_name`), and Store (`store_id — store_name`). |

## 4. Users

- **Super Administrator** — Full access; manages users, roles, and permissions.
- **Sales Manager** — Manages items, batches, hierarchy, and distributors (no Excel import in seed).
- **Read Only (VIEWER)** — View-only access.
- **Integration/system processes** (future) — Will write via separate `intr_flag` flows.

## 5. Non-functional Needs

- Login page + collapsible sidebar dashboard, with a modern and optimized layout.
- Responsive design; Facebook-like font/background colors and an eye-comfort palette.
- Sidebar accordion: opening one navigation group automatically collapses the others, with smooth transitions.
- Font Awesome icons served **locally** (no CDN).
- Search, filters, and pagination on every list.
- Column filters support typeahead search and multi-select.
- High-density compact view: minimal margins and padding across tables, cards, and filter controls to maximize visible data and eliminate wasted screen space.
- Runs in a Python virtual environment.
- Default admin credentials per `AGENTS.md`, to be changed after first login.

## 6. Success Criteria

- A super admin can create the sample hierarchy (TCPL example), an item with its default batch, and a distributor with its default stores without touching SQL.
- Every action above appears in the audit log with old/new values and the acting user.
- A VIEWER-role user cannot create or edit anything and cannot open admin screens.
- Excel templates download and import round-trips cleanly, reporting per-row errors.
